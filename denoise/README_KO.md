# FPGA CNN 이미지 잡음 제거기

잡음 섞인 흑백 사진을 넣으면 FPGA가 깨끗한 사진을 돌려줍니다. CIFAR 분류에 썼던 **같은 비트스트림**
(K=1152, COUT=128, P=16, T=4, 런타임 형상)을 그대로 쓰고, 망만 분류용에서 잡음 제거용으로 바꿨습니다.

## 설정

표준 설정인 DnCNN(Zhang et al., 2017)과 같습니다.

| 항목 | 내용 |
|---|---|
| 학습 사진 | Train400 (BSD 180×180 흑백 400장) 중 380장, 20장은 검증용. 40×40 또는 50×50 패치, 4가지 크기 × 8가지 뒤집기/회전 |
| 테스트 사진 | Set12 (12장), BSD68 (68장) |
| 잡음 | 가우시안 백색 잡음 σ=25 (0~255 기준) |
| 학습 종료 | 검증 PSNR이 6 epoch 동안 안 오르면 학습률 반감, 15 epoch 동안 안 오르면 종료. 검증 최고 모델 사용 |

하드웨어 때문에 바꾼 것이 두 가지 있습니다. **비교 대상도 모두 이 조건에서 다시 측정했습니다.**

1. **잡음 사진을 [0,1]로 자르고 7비트로 양자화합니다.** 코어 입력 포트가 7비트 부호 없는 값이기 때문입니다.
2. **마지막 층이 깨끗한 사진을 직접 출력합니다.** DnCNN은 잡음을 예측해서 빼지만, 코어는 모든 출력에 ReLU를 걸기 때문에 음수가 있는 잡음은 낼 수 없습니다. 잡음 사진을 마지막 층에 한 채널 더 넣습니다(skip).

- **QAT의 효과:** 정수 손실(Set12 / BSD68)이 같은 예산판 시드 1 maxout 0.16 / 0.14 → 0.01 / 0.01, ReLU 0.05 / 0.02 → 정수가 float보다 0.04 / 0.02 높음, B 0.04 → 0.01 dB(조기 종료판 maxout 0.22 → 0.02). ReLU·maxout 시드 2·3과 45채널 망까지 PTQ 손실은 0.02–0.25 dB이고(평균 결합 시드 2는 0.29 / 0.17), QAT 뒤 ReLU·maxout·45채널 모델은 모두 0.04 dB 이내다. 평균 결합 시드 2의 QAT 모델은 표의 'float'(양자화를 끈 FoldedQ)이 BSD68 27.78로 정수 28.82보다 1 dB 낮은데, 양자화를 끄면 활성값 클리핑(0–127·a)까지 꺼지기 때문이다: BSD68 한 장이 8.74 dB로 무너지고, 클리핑만 남기면 평균 28.75 dB다. 보드가 계산하는 정수 값과는 상관없지만, 이 모델의 float 열은 비교 기준이 아니다. 이 QAT는 epoch 2가 검증 최고였다(정수 검증 28.251 → 28.392, float 28.436).
- **BM3D 조건:** 클리핑 7비트 입력은 BM3D에 BSD68 0.26 dB 손해를 준다(`bm3d_protocol.py`; 포화 픽셀이 많은 영상에 집중). σ를 학습 영상 40장에서 다시 골라도(σ=23) −0.06 / +0.09 dB로 0.1 dB 이내.
- **같은 입력의 DnCNN-S:** `dncnn_s_protocol.py`. 공개 가중치(float, 556k, 클리핑 없이 학습)가 30.35 / 28.89(클리핑 없는 입력 30.44 / 29.24로 문헌 재현). 화질 모델은 Set12 0.2 dB 낮고 BSD68 0.1 dB 높지만, 후자는 학습 분포 차이라 이득으로 세지 않는다.
- B-32 ReLU·maxout은 시드 세 개(학습 1·2·3, QAT 단계는 모두 3), 평균 결합은 두 개, 나머지는 하나다. 시드 하나인 망끼리의 0.1 dB 미만 차이는 해석하지 않는다.

### SSIM (`ssim_eval.py` → `ssim_eval.json`)

Wang et al. (2004)의 SSIM: 8비트 영상, 11×11 가우시안 창(σ 1.5), K1 0.01, K2 0.03, 범위 255, 영상 평균(`skimage.metrics.structural_similarity`, `gaussian_weights=True, use_sample_covariance=False`). 정수 모델은 보드 드라이버의 host 에뮬레이션(보드와 비트 일치)으로 출력을 다시 만들고, BM3D·DnCNN-S는 float 출력을 8비트로 반올림한다. 모든 출력은 같은 시드 0 잡음에서 다시 만들며, 사진별 PSNR이 저장값(`int_eval.json` 10⁻⁵ dB, `baselines.json`·`bm3d_protocol.json`·`dncnn_s_protocol.json` 10⁻³ dB)과 맞지 않으면 멈춘다. 정수 모델의 최대 차이는 1.5×10⁻⁶ dB였다. 출력 영상은 픽셀까지 같고, 차이는 `common.psnr`이 float32로 평균을 내는데 int_eval.json을 만든 PC의 numpy가 그 합을 다르게 반올림한 데서 온다(확인: `dn_d10_c45_us_fx_qat`의 Set12 12장을 양자화기의 정수 모델과 보드 드라이버로 다시 만들면 두 출력은 모든 픽셀이 같고, 둘 다 int_eval.json과 최대 4.8×10⁻⁷ dB 다르다). 처음에 적었던 '공용 `to_image` 이전 export의 반올림 경계 픽셀' 설명은 틀렸다. 같은 이유로 `run_denoise.py`의 최종 PSNR 대조도 10⁻⁶에서 10⁻⁵ dB로 넓혔다. 이 정도 차이 검사만으로는 한 픽셀의 1 LSB 차이를 다 잡지 못하므로 픽셀 일치의 증거는 아니다. 보드 쪽의 비트 일치 증거는 그대로 층별 대조다. 4코어에서 약 40분.

### 왜 이런 설계인가: 사이클 모델

창 하나의 비용은 `max(K, ⌈COUT/P⌉ × ⌈K/T⌉)` 사이클(P=16, T=4)이다. 입력 포트가 사이클당 값 하나를 받으므로 K보다 빨라질 수 없고, **COUT ≤ P·T = 64이면 출력 채널은 비용이 없다.** 보드 실측은 여기에 창당 +1, 그리고 창당 최소 COUT 사이클(코어가 출력을 사이클당 하나씩 내보냄)이 더해진다. 보정 전 모델의 오차는 0.4–1.6%(B-32 ReLU 0.38%, B 0.70%, B-32 maxout 1.37%, A 1.63%), 보정 모델은 네 망(A, B, B-32 maxout, B-32 ReLU)에서 0.003% 이내(`train_denoise.board_cycles_per_pixel_measured`).

- A의 중간 층(K=288, COUT=32)은 계산에 144 사이클이면 되는데 입력에 288이 걸린다. 곱셈기 활용률 41%.
- **B (space-to-depth):** 창 수가 1/4이 되므로 같은 사이클 예산에 채널 64, 10층 망이 들어간다. K=576, COUT=64에서 입력과 계산이 정확히 균형(망 전체 활용률 88%). 파라미터 6.4배, 곱셈 1.6배인데 사이클은 25% 적다. B 대 A의 화질 차이는 리샘플링만의 효과가 아니라 더 큰 망의 효과다.
- **B-32 + maxout:** 채널 32(K=288)로 돌아오면 출력 64까지가 다시 공짜. 은닉층이 채널마다 후보 두 개를 내고(출력 64) PC가 재양자화할 때 큰 쪽만 넘긴다(`max(ReLU(a), ReLU(b))` = maxout). 다음 층 K는 그대로. 보드에서 이 층은 **289 사이클/창**으로 A의 출력 32 층과 같았다. 첫 층(K=36)만 출력 64개를 내보내는 64 사이클이라 픽셀당 669 → 675. 활용률 45% → 87%.
- **병목의 출처:** 입력이 사이클당 값 하나인 것은 이 설계의 선택이다. 코어의 창 입력 포트(`rtl/banked_window_mac.sv`의 `s_data[6:0]`)가 사이클당 값 하나를 받고, AXI-Stream 래퍼(`rtl/window_mac_axis.sv`)는 전송 단위(beat)당 값 4개를 그에 맞춰 1개/사이클로 풀어 넣는다. 포트를 넓히려면 래퍼만이 아니라 코어의 적재 경로도 바꿔야 한다(처음에 '래퍼의 설계'라고만 적은 것은 부정확했다). 포트를 넓혔을 때 출력 64 층(4값부터는 모든 은닉층)의 비용을 정하는 계산 항은 같은 형상의 VGG11 `features.3` 창(K=576, 출력 128, dense·sparse 창 교대) 중 계산에 묶인 창에서 이 코어(P=16, T=4)의 RTL 시뮬레이션과 창당 1 사이클 안에서 맞았다(956.2 대 956.8, `scripts/cifar_budget.py --validate`). 4값 포트 변형을 만들어 실제 창의 RTL 시뮬레이션과 보드에서 확인했다(아래 '4값/사이클 포트'). 포트를 4-wide로 넓히면 K=288·COUT=64 층은 연산 바운드(dense 288 대 ReLU 144)가 되어 maxout은 공짜가 아니다. 공짜 출력 채널의 한계는 대략 곱셈기 수 / 입력 폭(1값 64, 2값 32, 4값 16)이다. 창을 PC가 만드는 것도 같은 역할이다. 05.png의 모든 창을 세면(`python denoise/wider_ports.py`, sparse 모드; 괄호는 dense 상한) 사이클/px는 A, B, B-32 ReLU, B-32 maxout 순으로 2값에서 907 (907), 741 (1,245), 339 (339), 524 (633), 4값에서 573 (828), 683 (1,207), 203 (317), 503 (613), 칩 안 라인 버퍼(창마다 새 값 C_in개)에서 538 (827), 665 (1,206), 191 (316), 500 (612)다. 즉 2값부터 maxout은 ReLU의 1.55배(dense 1.87배)로 공짜가 아니고, B는 2값에서 아직 A의 0.82배(dense 1.37배)지만 4값에서 1.19배, 라인 버퍼에서 1.23배로 A보다 느려진다(`PAPER_KO.md` 표 III). 규칙은 이 입력 구조에 조건부다. 처음 판은 보드에서 잰 활성값 밀도에 뱅크 불균형 1.0–1.3을 가정해 sparse 값을 추정했는데, 그룹당 비용을 ⌈K/4⌉로 자르지 않았고 두 망에 같은 불균형을 가정해 maxout ÷ ReLU를 4값에서 2.59–2.79, 라인 버퍼에서 2.85–2.88로 높게 잡았다. dense 값도 창당 +1을 계산에 묶인 창에까지 붙여 최대 0.9% 컸다(RTL에서 +1은 적재에만 붙는다).
- **host의 몫:** im2col, 재양자화, maxout의 max를 합쳐 장당 0.07–0.13 s(4코어, numpy, 대부분 재양자화)로 50 MHz 코어 시간의 5–9%다(`python scripts/time_host.py`). 표의 벽시계는 JTAG 전송과 보드 쪽 검증 시간이다.
- **보드 실행 모드:** 모든 실행이 sparse 모드(`mode_seq=1`, 0인 활성값의 곱셈을 건너뜀)였다. 입력 항 K는 그대로라 입력에 묶인 층의 사이클은 dense와 같다. 같은 비트스트림의 CIFAR-10 실행에서 K=576, COUT=128 층은 sparse로 591.5 사이클/창이었다(dense COUT>64는 보드 미측정).

### 4값/사이클 포트 (W=4) — 보드 실측

심사 지적("병목은 이 설계가 스스로 정한 것이고, 병목을 바꿨을 때의 측정이 없다")에 실험으로 답하려고, 창 입력 포트가 사이클당 값 4개를 받는 코어를 만들어 보드에서 돌렸다. 예측은 이 비트스트림을 만들기 전에 커밋했고(7e81f6b, `predict_w4.py` → `w4_prediction.json`), 측정과 비교하는 기준도 측정 전에 `compare_w4.py`에 적어 두었다. **결과: 네 망 모두 불일치 0, 총 사이클은 예측보다 0.0009–0.0044% 많았고, B ÷ A는 0.75에서 1.19로(B가 A보다 느려짐), maxout ÷ ReLU는 1.01에서 2.48로 바뀌어 두 기준(B ÷ A > 1, maxout ÷ ReLU > 1.5)을 모두 넘었다.**

- **바뀐 것:** `rtl/banked_window_mac.sv`에 파라미터 W(1 또는 T). W = T = 4이면 한 beat의 탭 4r..4r+3이 네 뱅크의 같은 행에 하나씩 들어가므로 "뱅크마다 사이클당 튜플 하나"는 그대로이고, 창 적재가 K+1에서 K/4+1 사이클로 준다. 래퍼(`rtl/window_mac_axis.sv`)는 beat를 통째로 넘긴다. 창이 beat 경계에서 끝나야 하므로 호스트가 창과 가중치를 4의 배수 길이로 0 패딩한다(`run_denoise.py --w4`; 0×0이라 결과는 같다). W=4에서 RUN_K는 4의 배수로 올림되어 코어와 래퍼가 창의 끝을 늘 같은 곳으로 본다. 패딩을 잊으면 써 넣은 RUN_K와 읽은 값이 달라 실행 전에 드러난다(그대로 실행하면 입력이 모자라 끝나지 않는다). ID 레지스터 비트 9가 W=4를 표시한다. 보드 스크립트는 비트 9인데 K가 4의 배수가 아니면 멈추고, 빌드를 지정하지 않으면 `*_w4_*` 빌드를 고르지 않으며, `run_denoise.py`는 실행마다 ID와 `--w4`가 맞는지 확인하며 IN_STALL/OUT_STALL을 기록한다. 기본값 W=1 빌드의 신호는 바뀌지 않는다.
- **시뮬레이션 검증 (보드 아님):**
  - 코어 단독(Icarus, `scripts/run_stream_checks.py --suite smoke`): W=4 18개 사례(0 패딩으로 K=4·12·28, P 1–8, DEPTH 1–8, 출력 정지·입력 공백·중간 리셋 포함)에서 모든 출력이 정수 오라클과 같고, 창마다 시작·끝 사이클이 사이클 모델(`scripts/stream_model.py`, 적재 K/4 beat)과 정확히 같다. W=1 141개 사례도 그대로 통과.
  - 래퍼(`scripts/run_axis_checks.py` smoke·geom·real): W=4 18개 사례가 모두 통과했다. 그중 스로틀이 없는 14개에서 CYCLES가 코어 단독 측정과 같고(래퍼 비용 0), 입력 스로틀이 없으면 IN_STALL = 0이다(매 사이클 beat 하나를 받음). K = 9·27 데이터는 RUN_K에 9·27을 써도 12·28로 읽힌다. 보드 빌드 형상(P=16)에서 VGG11 창(K=576, 출력 128) 64개는 W=4로 62,716 사이클이었다.
  - 실제 창(`python denoise/sim_w4_layers.py` → `w4_rtl_sim.json`): 네 망의 모든 층(37개)에서 05.png의 창 512개씩(층에 고루 퍼진 연속 구간 4개)을 보드 빌드 설정의 래퍼(K ≤ 1152, COUT ≤ 128, P=16, T=4, sparse 모드)에 W=4와 W=1로 넣었다. 모든 출력이 정수 오라클과 같았고, CYCLES는 예측에 쓴 창당 계수(`predict_w4.window_cycles`)의 합과 층마다 W=4에서 10–164, W=1에서 16–407 사이클 차이였다. 차이는 실행마다 한 번 붙는 채움·비움이라 창 수와 무관하다. 은닉층에서는 W=1과 W=4 모두 min(창 적재 ⌈K/w⌉+1, 마지막 창의 계산) + 19 사이클이다(아래 보드 실측의 규칙, `w4_gaps.py`). W=1은 적재가 늘 길어 마지막 창의 계산 + 19(층 전체를 돈 W=1 보드의 은닉층에서는 마지막 창이 0 패딩이 많은 영상 모서리라 57–199), W=4 표본은 마지막 창의 계산이 대개 적재보다 길어 적재 + 19 = 92(K=288; 계산이 72인 두 층은 91), K=576에서 164다. 즉 W=4 예측의 창당 계수는 RTL과 맞는다. 남은 물음은 DMA가 매 사이클 beat를 대 줄지였다(아래 보드 실측).
  - UVM(Verilator 5.052, UVM 1.2, `scripts/run_uvm.py`): W=4 빌드 3종(small_w4, fixed_w4, board_w4)의 smoke·reg·random(·CIFAR 형상) 시험 30개가 모두 통과. 시퀀스가 호스트처럼 0 패딩하고 RUN_K는 K나 패딩한 길이 중 하나로 쓴다. W=1 빌드 4종의 39개는 비교한 출력 수까지 이전과 같다. IEEE 1800.2-2020.3.1에서도 시드 2개로 46개(W=4 20개)가 통과했다.
  - 뮤턴트(일부러 심은 버그)에 W=4 경로의 버그 5개를 더해 15개 모두 검출했다(W=4 버그는 small_w4 빌드에서). 결과는 `sim/uvm/RESULTS_UVM_KO.md`.
- **보드 실측 (2026-10-17, 50 MHz, Set12 05.png, sparse 모드; `RUN_W4_DENOISE.cmd` → `board_runs/*_05_w4.json`, `python denoise/compare_w4.py` → `w4_measured.json`):** 네 망의 모든 층에서 불일치 0, PSNR은 W=1과 소수점 끝까지 같다. 실행마다 ID 0x4d410303(비트 9 = W=4)을 확인했다. 총 사이클은 예측보다 A +337, B +1,372, B-32 maxout +794, B-32 ReLU +586 사이클(0.0009–0.0044%) 많았고, 층마다 +9–164 사이클이다. 이 차이가 무엇인지는 `python denoise/w4_gaps.py`(→ `w4_gaps.json`)로 확인했다. 층의 창은 모두 같은 시간에 적재되고 다음 창의 적재가 현재 창의 계산과 겹치므로, 창마다 max(적재, 계산)을 더한 계수는 마지막 창의 적재와 계산 중 짧은 쪽을 한 번 빠뜨린다. 실행 뒤에 읽어 보니, W=1·W=4 보드 실행 각각이 계수와 보인 차이(IN_STALL을 뺀 값)는 은닉층 29개 모두에서 min(창 적재 ⌈K/w⌉+1, 마지막 창의 계산) + 19 사이클이고, 마지막 층 4개는 + COUT + 3이다(66/66; 위 RTL 표본도 66/66). W=1은 적재가 늘 길어 마지막 창의 계산 + 19가 된다(위의 '마지막 창의 계산 + 19'). 첫 층(규칙 밖; W=4에서는 출력 COUT에 묶임)은 W=4에서 9–17, W=1에서 15–44 사이클이다. W=4 보드의 차이가 RTL 표본보다 작은 층은 출력에 묶인 첫 층과, 영상 모서리의 마지막 창이 0이 많아 계산이 적재보다 짧은 층(A·B-32 ReLU의 은닉층, B의 conv7–8, 마지막 층)이다. 이 규칙은 실행 뒤에 읽어 낸 설명이고 예측이 아니다. DMA는 거의 매 사이클 beat를 대 줬다. 코어가 입력을 기다린 사이클(IN_STALL)은 네 망을 합쳐 12(B-32 ReLU conv5)이고, `compare_w4.py`에 미리 정한 대로 보정하지 않고 그 층의 CYCLES에 그대로 두었다(그 층의 차이 77 = 65 + 12). OUT_STALL은 0이다. 벽시계(JTAG 하네스)는 A 585 s, B 475 s, B-32 maxout 359 s, B-32 ReLU 315 s다. 타이밍: W=4 비트스트림(`build/zed_v4_p16_t4_w4_1792234898`, 옛 PC의 Vivado 2026.1)은 100 MHz에서 배치배선 WNS +0.130 ns이고, 설계 전체는 LUT 11,151개(21%), RAMB36 68 + RAMB18 6(BRAM 51%), DSP 0이다(래퍼를 포함한 `window_mac_top` 7,043 LUT, 그중 코어 `banked_window_mac` 6,777 LUT; RAMB36 64 + RAMB18 4는 모두 코어; 리포트는 `board_runs/w4_build/`). 같은 날 같은 설정으로 다시 만든 W=1 빌드는 원래 보드 빌드와 같은 +0.221 ns였다(빌드 로그 기준).

**시드 2·3은 GPU PC에서 (2026-10-16, 결과를 보기 전에 정함).** 옛 PC의 시드 2·3 실행이 중간에 끊겨, ReLU·maxout 시드 2·3, 평균 결합 시드 2, 45채널 망을 GPU가 있는 다른 PC에서 처음부터 다시 돌린다(평균 결합 시드 3은 처음 계획에도 없었다; 판단 규칙은 평균 결합의 시드 2만 쓴다). 같은 시드의 망들이 같은 장치에서 학습되게 하려는 것이며, 옛 PC에서 끊기거나 끝난 시드 2·3 실행은 결과와 상관없이 쓰지 않는다. 시드 1은 CPU에서 학습했다. GPU에서는 `train_denoise.py`가 TF32를 끄고 cuDNN의 결정적 합성곱 알고리즘을 쓰며(CPU와 같은 fp32 연산), 장치·GPU·torch 버전을 `_train.json`의 `hardware`에 남긴다. **실제 시드 2·3과 45채널 실행은 이 설정을 넣은 커밋(261952a) 전에 받은 코드로 돌았다**(2026-10-17 확인: `_train.json`에 `hardware`가 없다). 즉 PyTorch의 GPU 기본값으로 학습됐다(합성곱은 GPU가 지원하면 TF32, cuDNN 알고리즘은 비결정적). GPU에서 돈 것은 체크포인트 텐서의 저장 위치(`cuda:0`)로 확인했다. 이미 정한 대로 이 실행들을 시드 2·3으로 쓰며, 결과를 본 뒤 다시 돌려 바꾸지 않는다. 첫 epoch 학습 손실(GPU 대 CPU): ReLU 시드 2 0.009679 대 0.009686, 평균 결합 시드 2 0.010157 대 0.010170, maxout 시드 2 0.012506 대 0.012657(1.2% 차이; 시드 1 maxout 0.012602와도 다르다). 시드와 플래그는 `args`로 확인했다. 가중치 초기값과 패치·잡음은 시드만으로 정해지므로 장치가 달라도 같고, 다른 것은 부동소수점 연산뿐이다(아래처럼 실제 GPU 실행은 TF32였다면 정밀도도, 비결정적 cuDNN이라 연산 순서도 다르다; 확인: 다른 CPU에서 다시 돌린 시드 1 maxout의 epoch 1 학습 손실이 0.012599로 원래 0.012602와 같았고, 검증 PSNR은 연산 순서 차이로 23.896 대 23.794 dB였다). 시드 2의 epoch 1 학습 손실(CPU): ReLU 0.009686, maxout 0.012657, 평균 결합 0.010170. QAT와 양자화는 어느 PC에서든 CPU로 돈다. 평균 결합 시드 1의 QAT는 체크포인트(`dn_d10_c32_us_avg_fx.pt`)가 있는 옛 PC에서 한다.

스크립트가 하는 일:
- `train_denoise.py`: 망은 노드 그래프입니다(`node`, `unet_spec`). 각 노드는 코어 한 번(창 kh×kw, stride, dilation, COUT)이고, 입력 맵 여러 개를 이어 붙일 수 있으며, 후처리(maxout, pixel shuffle)는 PC 몫입니다. 사이클 모델과 보정 모델을 출력합니다.
- `qat_denoise.py`: 보드의 정수 연산(INT8 가중치, 7비트 활성값, 바이어스 단위, skip 스케일 접기, 재양자화 뒤 maxout, 8비트 출력)을 float 안에서 straight-through로 재현한 `FoldedQ`를 미세조정합니다. 활성값 스케일은 학습 변수(LSQ). 검증은 양자화를 켠 채로 하므로 남는 모델이 보드 모델입니다.
- `quantize_denoise.py`: 그래프를 정수로 바꾸고, 합성곱 형태와 보드가 스트리밍하는 im2col 형태가 모든 노드에서 같은지 확인한 뒤 export합니다. QAT 체크포인트는 범위 탐색 없이 학습된 스케일을 씁니다.
- `scripts/run_denoise.py`: 그래프를 순서대로 보드에서 실행합니다. 층마다 im2col을 만들어 CIFAR 때와 같은 보드 경로로 실행하고, 보드 쪽에서 정답과 비트 단위로 비교하며, 최종 PSNR이 `int_eval.json`과 다르면 멈춥니다. 512×512는 DMA 한도 때문에 창을 나눠 실행합니다.

## 실험 기록

### 잔차(잡음) 학습 — 정수에서 손해

마지막 층을 부호만 다른 두 채널 (w, b), (−w, −b)로 만들어 PC에서 ReLU(z) − ReLU(−z) = z로 잡음을 복원하는 방식(`--residual`, `dn_d7_c32_res`). float에서는 기존과 같았지만(−0.02 dB) 정수에서 0.3 dB를 잃었습니다(29.34 대 29.55). 원인은 확인하지 않았습니다.

### maxout — 7층 32채널에서는 효과가 작음

7층 × 32채널(K=288, 출력 64)에서 15 epoch 같은 조건 비교: 검증 PSNR이 12/15 epoch에서 maxout이 높았지만 마지막 5 epoch 평균 차이는 +0.02 dB(최고 epoch 기준 +0.12, 스크린 변동 약 0.4 dB 안; `screening/screen_A_*_train.json`). 10층 32채널(B-32)에서는 같은 예산의 QAT 대 QAT가 시드 1·2·3에서 +0.37 / +0.26, −0.03 / −0.02, +0.10 / +0.07 dB(평균 +0.15 / +0.10)로 시드 2에서 뒤집혀, 규칙 (c)에 따라 화질 이득은 주장하지 않습니다(조기 종료판끼리의 +0.54는 예산이 다른 비교). 64채널에서는 출력 128이 K를 넘겨 공짜가 아닙니다.

### 층별 활성값 범위 선택

맵마다 퍼센타일을 검증 영상 40장에서 따로 고릅니다(후보 11개, 공통값 뒤 맵별 보정). 예전 B 체크포인트에서 정수 손실 0.15 → 0.02 dB. 채널 간 범위 맞추기(cross-layer equalization)는 skip 가중치를 거칠게 만들어 더 나빴습니다.

### 2단계 U-Net — 같은 사이클에서 뒤짐

리샘플링이 공짜라는 성질로 깊이를 1/16 해상도에 두는 U-Net(`--arch unet`, 1,294 사이클/px, 669k 파라미터)을 30 epoch 비교: 검증 27.89 dB 대 B 28.14 dB(`screening/scr_unet_g2_train.json`). 경사 갱신이 100 대 160으로 적긴 했지만 이득의 조짐이 없어 보류했습니다.
